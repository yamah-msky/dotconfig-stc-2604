~/.config 詳細マニュアル

この ~/.config を Ubuntu マシン上で再現し、pin されたバージョンを維持し、 壊れたときに直すための参照資料。ブラウザで開いて Ctrl+F で引くことを想定している。 端末用の短い早見表は bootstrap/MANUAL.md、設計の記録（英語）は bootstrap/README.md にある。

1. クイックリファレンス

覚えるコマンドは 3 つ。すべて冪等で、何度実行しても良い。

~/.config/bootstrap/bs.sh          # 環境を再現・修復する
~/.config/bootstrap/bs.sh update   # 全バージョンを最新にする → git diff を見て commit
~/.config/bootstrap/bs.sh doctor   # 今のマシンが manifest とどこで違うかを表で出す

補助として bs.sh list（step 一覧と root 要否）がある。

原則

bs.sh は commit された manifest に書いてあるものしか入れない。 バージョンが動くのは bs.sh update を実行したときだけで、勝手に上がることはない。

オプション

オプション意味
--only ID,…この step だけ実行する。前方一致なので --only tool: で全ツール
--skip ID,…この step を飛ばす（前方一致）
--dry-run変更コマンドを表示するだけ。何も変更しない
--no-sudoroot が必要な step を飛ばし、最後に「後で流すコマンド」を表示する
--arch ARCHアーキテクチャ検出を上書きする（テスト用）
--checkupdate 専用。書き換えず「何が古いか」だけ表示（古いものがあれば exit 1）
--jsondoctor 専用。機械可読出力

存在しない ID を指定した場合は「何も実行しなかった」ことを明示して exit 2 で終わる。 タイプミスが成功に見えないようにしてある。

よく使う組み合わせ

bs.sh --only tool:              # pin されたバイナリを全部入れ直す
bs.sh --only tool:fzf           # 1 つだけ
bs.sh --only nvim,nvim:plugins  # neovim 関連だけ
bs.sh --skip nvim:plugins       # 遅いものを飛ばす
bs.sh update --check            # 上流に対して何か遅れているか
bs.sh update starship uv        # 一部だけ上げる

2. 新規マシンのセットアップ

# 1. 最小の足場（これだけは手で入れる）
sudo apt update && sudo apt install -y git zsh

# 2. ~/.config をこの repo にする
cd "$HOME/.config"
git init
git remote add origin git@github.com:mbyamaguchi/dotconfig-stc.git
git fetch
git checkout main

# 3. あとはこれ 1 つ
./bootstrap/bs.sh

# 4. 新しいシェルへ
exec zsh

bs.sh は途中で 1 度だけ sudo のパスワードを聞き、以降は無人で走る （バックグラウンドで sudo のタイムスタンプを維持している）。所要時間は回線次第で 10〜20 分。 neovim のプラグイン復元と treesitter パーサーのビルドが大半を占める。 終わったら bs.sh doctor で確認する。

sudo が使えない環境で

./bootstrap/bs.sh --no-sudo

root が必要な 7 step（apt:base apt:cpp apt:media gh locale zdotdir shell）は飛ばされ、 それ以外はすべて実行される。locale には root 不要の代替経路もあり、 $XDG_DATA_HOME/locale に localedef で自前生成して zsh/.zshenv が LOCPATH 経由で拾う。

してはいけないこと

sudo ./bootstrap/bs.sh と実行してはいけない。すべてが /root/.local に入ってしまうため、スクリプトが検知して拒否する。 個々のコマンドが必要な場面で自分だけ昇格する設計になっている。

3. 日常運用

バージョンを上げる

bs.sh update          # manifest を書き換える
git diff              # 何が上がるかを確認
git commit -am 'Bump pins'
bs.sh                 # 適用

update が参照する上流は 5 系統（GitHub Releases / nodejs.org / npm registry / go.dev / git ls-remote）で、並行取得するので全体で数秒。 一部だけ上げるなら bs.sh update starship のように名前を渡す。

意図的に上げないもの

  • rust — stable 追従。この repo は rustc のバージョンに依存せず、 ~200MB のツールチェーンを bump ごとに再取得する価値がない。min だけが古すぎる版を捕まえる。
  • yt-dlp — latest 固定。古い yt-dlp はサイト変更で動かなくなるので、 ここでは追従が正解。manifest にもそう書いてある。
  • apt パッケージ — manifest の節を参照。

点検する

bs.sh doctor          # 差分があれば exit 1
bs.sh doctor --json   # 機械可読（将来 systemd timer で回す用）
STATUS意味
OKmanifest どおり
WARN違っている。bs.sh で直る可能性が高い
FAIL壊れている。放置すると使えない（locale・ZDOTDIR・git の identity など）
INFO参考情報。exit code には影響しない

何も変更したくない確認

bs.sh --dry-run                    # 変更コマンドを表示するだけ
bs.sh --dry-run --arch aarch64     # 別アーキテクチャでの挙動
bs.sh update --check               # 上流との差分だけ

4. リポジトリの地図

~/.config そのものが git repo になっている。ここには Chrome のプロファイルや gh のトークンのような「絶対に追跡したくないもの」も同居しているので、 .gitignore は全無視してから明示的に許可する allowlist 方式になっている。 

# all files
*

# .gitignore
!.gitignore

# bootstrap
# The `*` above ignores every level, so each directory needs its own negation
!bootstrap/
!bootstrap/*
!bootstrap/steps/
!bootstrap/steps/*
…
追加するときの注意

先頭の * はすべての階層を無視する。ディレクトリ自身の否定 （!manual/）が無いと git はそこへ降りていかないので、 !manual/* は永久に参照されない。新しいディレクトリを追跡するときは 2 行必要。

追跡されているもの

パス中身
bootstrap/再現の仕組み一式（§5）
manual/このマニュアル
zsh/.zshenv .zshrc aliases.zshシェル環境（§6）
sheldon/plugins.tomlzsh プラグイン 5 個の commit pin
nvim/init.lua lua/config/**エディタ設定（§7）
nvim/lazy-lock.jsonプラグイン 34 個の commit pin。この repo で最も価値の高い pin

意図的に追跡していないもの

  • git/config.local — 実アドレスと GPG 署名鍵を持つ。公開 repo に 入れてはいけないので untracked。雛形だけが git/config.local.template として追跡され、 bs.sh の git:local step がコピーする（既存ファイルは絶対に上書きしない）。
  • zsh/.zsh_history、gh/、google-chrome/、 fcitx5/ など — 履歴・トークン・プロファイル。
  • nvim.bak/、nvm/、bob/ — 生成物と外部管理のツリー。

bootstrap/test/container.sh は git archive HEAD をコンテナへ流し込むので、 追跡ファイルだけが検証環境に入る。トークンや履歴がコンテナに漏れない構造になっている。

GitHub Releases から取れるバイナリならtools.tsv に 1 行足すだけ。 step の登録・--only の ID・doctor の行・update 対応は すべてそこから生成される。

cd bootstrap/tool && go test ./...   # manifest の形式チェックが走る

「ダウンロードして展開する」以上のことが必要なものは steps/ にファイルを足す。 関数 1 つと register 1 行が最小構成——一番小さい例は steps/30-zdotdir.sh。

npm-globals.tsv — npm/pnpm のグローバル CLI

npm install -g(や、それと同じ挙動をする一部のインストーラ)は $NVM_DIR/versions/node/vX.Y.Z/lib/node_modules——その node バージョン専用のディレクトリ ——にパッケージを置く。zsh/.zshenv は nvm alias default が指す 1 バージョン分だけを PATH に glob で足す(lib.sh の path_init。 起動を約 620ms 速くするため nvm.sh を source しない)。そのため bs.sh --only node が runtimes.tsv の pin へ alias を切り替えた瞬間、 こうして入れた CLI は PATH から外れる——消えたように見えるが、実際は古いバージョンの下に 取り残されているだけ。これは steps/50-runtimes.sh の NODE_GLOBALS (prettier / eslint_d / tree-sitter-cli)がまさに一度踏んだ罠と同じもので、 この manifest はその修正——pnpm add -g で $PNPM_HOME(node バージョンに 依存しない)へ入れる——を、npm-globals.tsv に 1 行足すだけで 使えるようにしたもの。tools.tsv と同じく step の登録・--only の ID・ doctor の行・update 対応がそこから生成される。

列意味
namestep ID は npm:<name> になる。doctor の行 ID も同じ
packagenpm/pnpm 上のパッケージ名(スコープ付きも可。例: @openai/codex)
ref固定バージョン、または latest で毎回最新を解決(tools.tsv の yt-dlp と同じ opt-out)。latest でない行だけ bs.sh update が bump する
binバイナリ名がパッケージ名と違う場合に指定

追加したら確認する:

bs.sh --dry-run --only npm:<name>
bs.sh --only npm:<name>
bs.sh doctor   # npm:<name> が $PNPM_HOME から解決されているか

apt.tsv — バージョンを pin しないもの

グループ（base / cpp / media）ごとにパッケージを列挙する。 版は意図的に pin しない。 Ubuntu の archive は古い版を削除するので、 ripgrep=14.1.1-1 のような pin は resolute-updates がパッケージを差し替えた瞬間に壊れる。 pin はここでは再現性を下げる。固定しているのは集合であって版ではない。 版に敏感なものは tools.tsv に置く。

なぜ shell と Go の二言語か

  • install は shell。 中身はほぼプロセスの орchestration で、apt・curl・tar・git・nvim へ shell out する箇所が 100 以上ある。Go だとそれぞれが exec.Command + エラー処理になる。 より本質的な理由として、bootstrap が自分でインストールするツールチェーンを要求してはいけない。 この repo に CI は無く push もしないので、Go バイナリは新規マシン上で—— runtimes.tsv が置き換えようとする前の、apt の Go 1.26 で——ビルドされることになる。
  • doctor と update は Go。 こちらは HTTP・JSON・バージョン比較で、 shell 版の実際のバグはすべてそこにあった（0.9.3 が 0.10.0 より大きいと判定される、 v 接頭辞の有無、アセット名の展開ミス）。go test で挙動を固定できる場所に置いた。 どちらも新規マシンでは不要（初日に上流より遅れているものは無い）なので、 実行する時点では bs.sh が Go を入れ終わっている。

bs.sh doctor と bs.sh update は初回に tool/ をビルドして $XDG_CACHE_HOME/dotconfig/ にキャッシュし、.go が変わったら再ビルドする。 バイナリは commit しない（アーキテクチャ依存で、読んで検証できないから）。 パッケージは依存ゼロなので、ビルドにネットワークも go.sum も要らない。

代償

step のインストールは steps/*.sh、その検証は tool/doctor.go にある。 tools.tsv 由来の行は両方が manifest から生成されるので影響しないが、 個別 step については直す場所が 2 ファイルになる。

nvm.sh は 4700 行あり、読み込み時に nvm use default を走らせる （~620ms／シェル）。そこで .zshenv は $NVM_DIR/alias/default をファイルとして読み、 $NVM_DIR/versions/node/v<それ>*/bin を glob して PATH の先頭に置くだけにしている。 .zshrc 側では nvm を関数として定義しておき、 実際に nvm コマンドが呼ばれた時に初めて nvm.sh を source する。

zsh/.zshrc — 対話シェルだけが読む

  • has() — (( $+commands[$1] )) で zsh 自身のコマンドハッシュを見る。 $(command -v …) と違って fork しない。すべての optional なツールがこれで守られている。
  • sheldon → compinit の順序 — eval "$(sheldon source)" は compinit より前でなければならない。zsh-completions がここで fpath に自分を足すため。
  • compinit の高速化 — セキュリティスキャン（compaudit、~60ms）は 1 日 1 回だけ。dump は $XDG_CACHE_HOME/zsh/zcompdump に置き、 新しければバックグラウンドで zcompile する。
  • GPG_TTY — $TTY（zsh のパラメータなので無料）を export。 これが無いと commit の署名が Inappropriate ioctl for device で失敗する。 端末を持たないシェルには指すものが無いので .zshenv ではなくここ。
  • prompt / fzf / zoxide — starship・fzf --zsh・zoxide を has で守りつつ初期化。starship が無ければ素の PROMPT にフォールバック。
  • y 関数 — yazi で移動した先のディレクトリに cd する。 if has yazi（&& ではない）で書いてあるのは、 ツールが無いときに $? を非ゼロで残すと starship が最初のプロンプトを 「コマンド失敗」として描いてしまうから。

10. 落とし穴カタログ

いずれも無言で壊れる類のもので、実際にこの repo で踏んだもの。

① PATH にある ≠ 動く

has（shell）と Which（Go）が答えるのは「ファイルがあるか」だけ。 ネイティブバイナリを後から落としてくるラッパースクリプトは、その実体が 永久に来なくてもこの条件を完全に満たす。 これが原因で、コンテナ実走が「プラグイン 34 個・パーサー 0 個」のエディタを作り、 install step と doctor の両方が OK と報告した。

対策として runs（bootstrap/lib.sh）と Runs （bootstrap/tool/env.go）がツール自身に --version で名乗らせる。 ダウンロードしたバイナリのラッパーには必ずこちらを使う。 さらに、失敗をログに出しつつ exit 0 するコマンドについては、 step の生成物を数える（ビルドされた .so の個数）方が終了コードより信頼できる。

② gh auth setup-git が追跡ファイルに書く

~/.gitconfig が無い環境では、git のグローバル設定は ~/.config/git/config——この repo が追跡しているファイル——になる。 gh auth setup-git や git config --global は そこへマシン固有の設定を書き込んでしまう。git config --file ~/.config/git/config.local を使う。

③ nvm の alias がずれると新しいシェルだけ別の node を掴む

.zshenv は速度のために nvm.sh を source せず、 $NVM_DIR/alias/default を読んで glob する。 nvm install だけして nvm alias default を更新しないと、 今のシェルは正しい node、新しいシェルは別の node という状態になる。 bs.sh の node step は両方を必ず揃え、doctor がずれを検出する。

④ LOCPATH が存在しないディレクトリを指すと全ロケールが壊れる

glibc は LOCPATH が設定されているとそこだけを探し、 /usr/lib/locale を見なくなる。したがって存在しないパスを指すと C と C.UTF-8（glibc 組み込み）以外の全ロケールが死ぬ。 .zshenv が [[ -d … ]] && で守っているのはこのため。

⑤ pnpm 10 以降は build script を実行しない

未承認パッケージの postinstall はブロックされる。 ネイティブバイナリを postinstall で取得する npm パッケージ （tree-sitter-cli がまさにこれ）は、インストールが成功したように見えて 壊れたラッパーだけを残す。--allow-build=<pkg> で例外を明示する （build script をグローバルに有効化するのではなく）。

⑥ その他

  • sudo bs.sh はすべてを /root/.local に入れる。スクリプトが拒否する。
  • npm -g で入れたツールは単一の node バージョンのディレクトリに入るので、 node を bump すると消える。$PNPM_HOME/bin はバージョン非依存。 doctor の node:* 行がこれも見張っている。
  • .gitignore の否定は 2 行必要（§4）。
  • lazy.nvim 自身の版が lockfile とずれると、起動時に lockfile が書き換わる （§7）。

12. 既知の限界

  • Mason が入れる LSP サーバーはバージョン固定されていない。 mason.nvim に lockfile が無いため、lua/config/plugins/lsp.lua の ensure_installed はその日のレジストリの版を入れる。固定するなら "lua_ls@3.7.4" 形式か mason-lock.nvim の導入が必要。 treesitter パーサーは lazy-lock.json の nvim-treesitter の commit から ビルドされるので、実質的には固定されている。
  • install と検証が別言語にある。 step のインストールは steps/*.sh、 その検証は tool/doctor.go。tools.tsv 由来の行は両方が manifest から 生成されるので影響しないが、個別 step については直す場所が 2 ファイルになる。
  • x86_64 と aarch64 以外では、ビルド済みバイナリを要する step が SKIP される。 404 で落ちるのではなく理由を表示してスキップし、全体は成功扱いになる。
  • WSL の Windows 側フォント設定は手作業。 Windows のターミナルは Linux 側の フォントを読まない。bs.sh が TTF の場所とコピー先を表示するので、 Windows 側でインストールしてターミナルのフォントに指定する。 reg.exe 経由のレジストリ操作は自動化していない。
  • 読まれていないファイルの掃除は opt-in。 bootstrap/cleanup.sh は対象を表示するだけで、--yes で実行する。 削除ではなく ~/.local/share/dotconfig-legacy/<日時>/ へ移動するので戻せる。 ~/dotfiles/ と ~/bootstrap/ は判断が必要なので対象外にしてある。

このファイルは ~/.config/manual/index.html。git で追跡されているので、 新規マシンでは clone した直後から読める。 設計の記録（なぜこの構成なのか）は bootstrap/README.md、 端末用の早見表は bootstrap/MANUAL.md。
